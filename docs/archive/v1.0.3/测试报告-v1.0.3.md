### 1.2 沙箱造成的两条假失败（重要，避免误判）

测试运行在 DSH 的文件沙箱里，有两个限制会污染结果：

1. **WMI 读子进程 `CommandLine` 返回“拒绝访问”** → Harness 里“启动命令行的 `--datadir` 断言”“额外参数原样附加”两条假失败。后来用 `bambu-recorder.exe` 直接记录子进程 `Environment.CommandLine`，实测 **通过**（引号、中文、空格全部正确），见第 3 节回归基线。
2. **ShellExecuteEx 启动“工作区内的 exe”被沙箱拦截** → 用 sleeper/recorder 测“双击方式”时一律 Failed，message 为“没能用‘双击方式’启动 Bambu Studio…”。但**从 Harness 里 ShellExecuteEx 启动 `C:\Program Files` 下的真 Studio 是成功的**（E2E 通过），所以这是沙箱策略，不是产品缺陷。

## 2. 缺陷详情

### B01 [S2] 干净目录自检必失败 2 项，退出码 2 —— T9.1 不通过

**位置**：`src/SelfTest.cs:287-297`（用例），`src/LegacyScanner.cs:165-177`（实现）

**复现**：
```bat
build\harness\waitrun.exe build\BML-test.exe "--selftest build\selftest6"
```
其中 `build\selftest6` 是**全新空目录**，且 `tests\bambu-sleeper.exe` 已放在该目录根（T9.1 的前置条件全部满足）。

**期望**（测试指南 T9.1）：14 项全过；退出码 0。

**实际**：`selftest.log` 显示 **通过 12 项，失败 2 项**，退出码 **2**。

```
[失败] 能扫到以前留下的账号目录 → 应该是 2 个，实际 1。
[失败] 导入后出现在列表里，再扫一次不重复加 → 第一次应该导入 2 个，实际 1。
```

**根因**：`SelfTest.cs:287-297` 建了两个目录——`profiles\家里打印机`（含 `BambuStudio.conf` + `BambuNetworkEngine.conf`）和 `profiles\公司打印机`（**空目录**），然后断言 `found.Count == 2`。但 `LooksLikeStudioData` 只认 `BambuStudio.conf` / `BambuNetworkEngine.conf` / `plugins` 目录 / `printers` 目录四种，空目录不算，所以永远只能扫到 1 个。

**修复建议**：在自检的“公司打印机”里放一个 `BambuStudio.conf`（或 `plugins` 子目录）；或把断言改成 1 并同步文档。另外应先统一语义：空目录到底算不算“Studio 数据”。

**证据**：`docs\测试证据\selftest.log`（原始日志）；`build\selftest6\selftest.log`。

### B02 [S2] 已删除/移出的旧账号，每次启动被自动重新导入

**位置**：`src/MainForm.cs:50`（构造函数里 `LegacyScanner.Import(_settings)` 无条件执行）、`src/LegacyScanner.cs` Import/Scan；相关行为见 `src/MainForm.cs:657-700`（删除账号只从列表移除、不删数据）。

**复现**（Harness 可控用例，已实测）：
1. 在 `BAMBUMULTI_HOME\profiles` 下准备 `home`、`work`、`插件目录` 三个像 Studio 数据的目录；
2. 首次 `Import` → `added = 3`，命名“以前的账号（家）/（公司）/（插件目录）”；
3. 从 `settings.Profiles` 移除“家”并 `Save()`；
4. 再次 `Import` → **又新增 1 个（id=4）**，名字“以前的账号（家）”回来了。

**期望**：用户明确删除/移出的账号不应在下次启动时自己回来；至少应弹确认“发现旧账号数据，是否恢复”。

**实际**：每次启动都重新扫描并导入，用户删不掉。真实环境里也能看到同源痕迹：`%APPDATA%\BambuMultiLauncher\settings.ini` 的 `lastprofile=4` 但 4 号账号已不存在；日志 17:17 记录过“导入历史账号目录: C:\software\bambu账号管理\profiles\home”。（该目录现已被用户删除，所以真实环境当前扫描结果为 0 个孤儿，见 §9。）

**影响**：删除账号形同虚设；若旧目录里还有别人的登录凭据，会以“以前的账号（家）”重新出现在列表里，容易误点、误登录。

**修复建议**：在 `settings.ini` 增加“已忽略目录”列表（删除时记录 dir 的规范化路径），`Import` 跳过；或只在首次运行/用户点“导入旧数据”时扫描；最低限度每次导入前弹确认。

**证据**：`docs\测试证据\harness-console.txt:131-146`（LegacyScanner 段：`Import#1=3`、`Import#2=1`）。

### B03 [S2] 诊断把“进程活着但无窗口”判为成功，结论自相矛盾

**位置**：`src/Diagnostics.cs:237-241`

```csharp
// 实际逻辑
if (o.Started && !o.Exited && o.DirChanged) return true;
if (o.Started && !o.Exited) return true;   // ← 只要进程活着就算成功
```

**复现**：`LaunchDiagnostics.Run` 对一个永远不会创建窗口的进程（`bambu-sleeper.exe`）执行诊断。耗时 8,238 ms，报告同时出现：

```
状态：进程还在，但没看到窗口
结论：用“常规方式”能起来，双击方式在这台电脑上不行。
```

**期望**：没有窗口就不应判成功；应继续观察、或明确标注“进程存活但窗口未出现，无法确认”。

**实际**：第二个 `return` 吞掉了“无窗口”的情况，第一个 `return`（含 `DirChanged`）因此永远不可达；`Diagnostics.cs:212/217` 两个后续分支也全部不可达（`IsOkay(o1)` 已在 206 行返回）。

**修复建议**：删除第二个 `return`；成功条件至少要求 `HasWindow(pid, out _) || o.DirChanged`；无窗口时延长观察或给出“不确定”结论。

**证据**：`docs\测试证据\harness-console.txt:204-209`（Diagnostics 段）。

### B04 [S3] `--datadir=路径`（等号写法）解析错误

**位置**：`src/LaunchService.cs:276-288`（`ExtractDataDir`）

**复现**（Harness，3 条全失败）：

| 输入命令行 | 解析结果 | 期望 |
|---|---|---|
| `--datadir=D:\noSpace` | `=D:\noSpace` | `D:\noSpace` |
| `--datadir="D:\a b"` | `="D:\a` | `D:\a b` |
| `--datadir=D:\a b` | `=D:\a` | `D:\a b` |

实现是 `IndexOf("--datadir")` 后 `Substring(idx + 9).TrimStart()`，没有跳过可选的 `=`，于是 `=` 被当成路径首字符；带引号时还会把引号当普通字符截断。

**影响**：如果有人用 `--datadir=...` 启动 Studio（脚本、快捷方式、其他工具），本工具查不到该实例 → 再点“启动”会重复启动；由于 Studio 自己会把请求转给已有实例，表现就是“点了没反应”。“切到该窗口”也失效。

**文档冲突**：`docs/产品文档.md:341` 明写“`--DATADIR=...`、无引号、参数缺失等情况都覆盖（自检里有专门用例）”——自检里并没有等号用例（见第 4 节 D01）。

**修复建议**：取到参数后先 `TrimStart()`，若以 `=` 开头则去掉 `=` 再 `TrimStart()`，然后走引号/空格分支；补 3 条自检用例。

### B05 [S3] 勾选“复制”但默认目录不存在时，新账号目录不会被创建

**位置**：`src/AccountForm.cs:289-311`

```csharp
if (!useDefault && _chkCopy.Checked) {
    if (Directory.Exists(source)) { ... CopySharedData(source, dir, ...); }
    // 源目录不存在时：整段跳过，不建 dir
} else if (!useDefault && !Directory.Exists(dir)) {
    Directory.CreateDirectory(dir);
}
```

**复现**：全新机器（`%APPDATA%\BambuStudio` 不存在，用户还没运行过 Studio）→ 主界面“添加账号” → 填名字 → 勾选“复制插件与预设” → 确定 → 该账号 `Dir` 不存在 → 点启动 → 返回 `NoDir`：“这个账号的数据目录不见了…”

**期望**：目录被创建，账号可启动。`CopySharedData` 自身内部会 `EnsureDir(target)`（Harness 已验证：源目录不存在时调用它也能建出目标目录），所以只要进到复制分支就没问题。

**实际**：`Directory.Exists(source)` 为假时既没复制也没建目录；`else if` 的建目录只覆盖“未勾选复制”的情况。

**修复建议**：在 `if (!useDefault)` 分支末尾无条件 `Directory.CreateDirectory(dir)`；顺带把 `source` 不存在的情况在 UI 上提示一句。

**确认度**：代码路径确定；对照实验证明库函数能建目录。未做完整 GUI 点击复现（需要一台没装过 Studio 的机器或伪造 APPDATA）。

### B06 [S3] 改账号名不联动数据目录预览

**位置**：`src/AccountForm.cs:89`（只有 `_txtDir.TextChanged` 有联动）、`:195`、`:201-205`

**复现**（Harness 反射，STA 线程）：
1. 打开“添加账号”，默认名“账号 2”，目录预览 `...\profiles\账号_2`；
2. 把名字改成“家里”；
3. 目录预览**仍是** `...\profiles\账号_2`，保存后 `Profile.Dir` 就是 `账号_2`。

**期望**：名字变化时，若用户没有手动改过目录，预览应跟着变成 `...\profiles\家里`。

**实际**：`_txtName` 没有绑定 `TextChanged`，`SuggestedDir()` 只在切换单选/点“默认位置”时算一次。

**影响**：账号名与目录名永久不一致，用户以后在资源管理器里找不到“家里”对应的目录；也直接违反测试指南 T2.4 的预期行为（T2.4 的字符替换本身另见 B13）。

**修复建议**：`_txtName.TextChanged` 里判断“目录框仍是上次自动生成的值”才刷新，避免覆盖用户手改。

### B07 [S3] 启动后 UI 同步等待窗口，最长冻结 10 秒

**位置**：`src/MainForm.cs:554-555`：`Started` 后立即 `ScheduleVerify()` + `BringToFront(r.Pid, 10)`；`LaunchService.BringToFront` 在 UI 线程每 300 ms 轮询 `MainWindowHandle`，直到 10 秒超时。

**复现**：真实 Studio E2E 中，从启动到出现第一个窗口（标题“配置向导”）用了 **19 秒**。因此点“启动选中账号”后，主界面会无响应最长 10 秒（按钮点不动、列表不刷新），之后才恢复。

**期望**：启动动作立即返回，窗口切换异步进行；等待期间界面可操作。

**修复建议**：把 `BringToFront` 放进 `Task`/`Timer` 异步轮询；或把等待降到 1–2 秒。`LaunchAll` 没有这个问题（它不调用 BringToFront），可对照。

**确认度**：代码路径确定；E2E 证明窗口确实晚于 10 秒出现，未用秒表测 UI 冻结时长。

### B08 [S3] `{}` 形式的 conf 修补后带尾逗号，产出非法 JSON

**位置**：`src/Diagnostics.cs:56-76`（`PatchSingleInstance`）

**复现**（Harness）：
- 输入 `{}` → 输出 `{\r\n  "single_instance": false,}` —— **尾逗号，非法 JSON**；
- 输入 `{"other": 1}` → `{\r\n  "single_instance": false,"other": 1}` —— 合法；
- 真实 `BambuStudio.conf`（37,657 B）已是 false 时原样返回；手工改 true 再修补，与原文逐字节一致 → 真实配置安全。

**影响**：只有内容恰好是 `{}`（或首个 `}` 前没有成员）的 conf 会坏。Bambu Studio 解析失败后可能重置整份配置，用户丢失窗口/预设设置（本工具只碰 `single_instance`，但文件被写坏的是整份）。

**期望**：任何输入都产出合法 JSON。

**修复建议**：插入时判断插入点前是否已有成员/是否为空对象；或在 `'{'` 后插入 `\r\n  "single_instance": false\r\n` 再处理逗号。

### B10 [S3] `--render` 会改写用户真实 `settings.ini`

**位置**：`src/Render.cs:19-23`

```csharp
var s = Settings.Load();
s.FirstRunDone = true;      // 强制首次向导已完成
s.RememberWindow = false;   // 强制不记住窗口
s.Save();                   // 写回真实配置
```

**复现**：预置 `build\render-home\settings.ini`（`firstrun=1`、`remember=1`、1 个默认账号）→ `BML-test.exe --render build\render3` → exit 0，7 张 PNG 齐全，但 `settings.ini` 被改写：**remember 1→0，firstrun 被强制为 1**。（测试用 `BAMBUMULTI_HOME` 指向 `build\render-home`，与真实 `%APPDATA%` 配置目录等价。）

**期望**：出图/CI 工具不应修改用户配置；至少只在 `BAMBUMULTI_HOME` 下生效。

**实际**：直接写 `AppPaths.ConfigDir`。空配置时还会 `Seed` 两个假账号（“公司账号（默认）”“家里打印机”），并把首次向导标记为已完成——开发者在自己机器上跑一次 `--render`，下次打开正式程序就不弹向导了。

**修复建议**：`Render` 用独立的临时 `Settings` 对象，不调用 `Save`；或强制要求 `BAMBUMULTI_HOME` 环境变量，未设置则拒绝运行出图。

**证据**：`build\render-home\settings.ini`（运行后 `remember=0`、`firstrun=1`）；`build\render3\*.png`。

### B11 [S4] 相对目录被原样保存

**位置**：`src/Core.cs` `Settings.Load`（`[profile:N] dir=` 直接赋值，未 `GetFullPath`）

**复现**（Harness）：`dir=profiles\家里` → 加载后 `Profile.Dir` 仍是相对路径 → `Launch` 拼成 `--datadir "profiles\家里"`，Studio 会相对**工作目录**（exe 所在目录）解析，而不是相对 `%APPDATA%\BambuMultiLauncher`。

**影响**：手改配置/从别的机器拷贝配置后，数据目录会悄悄指到别处，表现为“登录状态没了”。正常 UI 流程写入的都是绝对路径，所以触发条件是手改/迁移。

**修复建议**：加载时 `Path.GetFullPath`（相对于 `ConfigDir`），或校验为绝对路径并拒绝加载。

### B12 [S4] `SafeFolderName` 未过滤 Windows 保留名

**位置**：`src/LaunchService.cs:828-843`

### B13 [S4] `Trim('_','.')` 吃掉尾部下划线，与 T2.4 期望不符

**位置**：`src/LaunchService.cs:839`

**复现**：输入 `a/b:c*?"<>|`，`SafeFolderName` 先把非法字符逐个换成 `_`，得到 `a_b_c______`，随后 `Trim('_','.')` 把尾部下划线全部删掉 → **`a_b_c`**。

**期望**（测试指南 T2.4）：目录预览应为 `a_b_c______`，且创建成功。

**实际**：`a_b_c`。功能上可用，但违反验收标准；用户若依赖目录名区分（如 `a_b_c_` 与 `a_b_c`）会冲突。

**修复建议**：只 `Trim('.')` 与首尾空格，或对结果仅去掉明显的边界点号。

### B14 [S4] conf 修不了却提示“没有这个字段”

**位置**：`src/Diagnostics.cs:18-53`（`EnsureSingleInstanceOff` 的 note 文案）

**复现**（Harness）：
- conf 为空文件 → 不改动，note：“配置里没有 single_instance 字段，没有改动。”
- conf 为 `{"single_instance": "true"}` → 不改动，同样文案。

**实际**：空文件是“没有 JSON 结构”，字符串值 `"true"` 是“字段存在但类型不对”，两者都不是“没有这个字段”。诊断报告会误导用户以为配置没问题。

**修复建议**：`PatchSingleInstance` 返回状态枚举（无字段/无 `{`/类型不对），note 分别给文案；类型不对时建议手动检查。

### B15 [S4] 重命名不查重

**位置**：`src/MainForm.cs:644-655`

**现象**：`RenameAccount` 只校验非空，直接改名并保存；两个账号可以同名（如都叫“家里”）。`AccountForm` 的新增流程有查重，改名没有。

**影响**：列表难分辨；`SafeFolderName` 目录不会跟着改，但名字重复会让用户混淆“哪个是哪个”。不造成数据损坏。

**修复建议**：改名时按 `OrdinalIgnoreCase` 与其它账号比较，冲突则提示。

### B16 [S3] 登录状态误判：32 字节的空壳凭据也显示“已登录”

**位置**：`src/Core.cs:133-141`（`HasLogin` 只判断 `fi.Exists && fi.Length > 0`）；显示在 `src/MainForm.cs:375-377`；环境报告 `src/AdvancedForm.cs:519`；自检 `src/SelfTest.cs:152-170`。

**复现**（用与真实样本相同的字节数，不碰真实目录）：
1. 准备一个 `BAMBUMULTI_HOME`，建两个账号目录：A 放一个 **32 B** 的 `BambuNetworkEngine.conf`，B 留空；
2. 启动主界面 → A 显示 **已登录**（黑色），B 显示 **未登录**（橙色）。
3. 截图：`docs\测试证据\login-status-misjudge.png`。

**真实案例**：用户机器上 `profiles\公司A1mini\BambuNetworkEngine.conf` 只有 **32 B**（账号实际未登录），主界面仍显示“已登录”；同一台机器上已登录的 `家里` 是 **768 B**、默认账号 **704 B**。

**为什么 32 B 不可能是有效凭据**：该文件前 16 字节是文件头（与 768 B 文件的前 16 字节逐字节相同），之后才是密文；32 B = 16 B 头 + 16 B 密文，只够一个 AES 分组（明文 16 B），而真实凭据的密文是 688 / 752 B。这个文件更像“退出登录/异常中断”留下的空壳。

**期望**：登录列显示“未登录”（或“凭据异常”），不要引导用户去点一个其实还要重新登录的账号。

**修复建议**：`HasLogin` 改为 `fi.Length > 32`（或 `>= 48`）；更稳的写法是“16 B 头 + 密文长度是 16 的倍数且密文 > 16 B”。同时在 `SelfTest` 补一条“32 B 空壳文件应判未登录”，并把产品文档 10.1 / 测试指南 T14 里“登录列基于文件存在性”改成“基于凭据文件大小”。

**影响**：用户以为已登录，点开却要重新收验证码；“这个账号配好了没有”的判断出现系统性偏差。
